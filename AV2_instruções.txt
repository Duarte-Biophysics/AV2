  criptografados em um SERVIDOR MONOLITICO HTTP, com API RESTful,

 FASE A - PREPARAR O PROJETO
==============================================================

PASSO 1 - Abrir o terminal na pasta AV2   [PRATICA]
  - No VS Code, clique com o botao direito na pasta AV2 e escolha
    "Open in Integrated Terminal".
  - Confira que o caminho do terminal termina com AV2.
  - Teste: node -v  e  npm -v  (devem mostrar versoes).

PASSO 2 - Criar o projeto Node + TypeScript   [PDF: Node.js e
          TypeScript]
  npm init -y
  npm i -D typescript tsx @types/node
  npx tsc --init
  - No tsconfig.json: target ES2022, module NodeNext,
    moduleResolution NodeNext, strict true, rootDir src,
    outDir dist, esModuleInterop true.
  - No package.json, scripts:
      "dev":   "tsx watch src/server.ts"
      "build": "tsc"
      "start": "node dist/server.js"
  - Confira se o .gitignore tem: node_modules, dist, .env
  - Git: se a pasta AV's ja for um repositorio, NAO rode git init
    na AV2 (evita repositorio dentro de repositorio).

PASSO 3 - Estudar a AV1 antes de codar   [PDF: "consolidara as
          abstracoes orientadas a objetos que projetou
          anteriormente"]
  Levantar da AV1 e anotar:
   a) Entidades e campos: Organizacao, Contrato, Lote,
      Equipamento, Movimentacao (e Usuario).
   b) Regras de transicao de status dos equipamentos.
   c) Calculos financeiros.
   d) Validacoes (CNPJ, codigo de barras, contrato, etc.).
   e) Autenticacao: como era a sessao/expiracao e qual biblioteca
      de hash de senha foi usada (o PDF manda usar a MESMA, ex.:
      bcrypt).
   f) Cenarios de teste/validacao (viram o seed no Passo 17).
  Dica Codex: diga a ele "crie tudo dentro da pasta AV2; use a
  AV1 apenas como referencia, sem alterar".

PASSO 4 - Definir a estrutura em camadas   [PDF: Controller-
          Service-Repository]
  Sugestao de pastas dentro da AV2:
    src/
      server.ts           (inicia o servidor)
      app.ts              (monta o Fastify)
      config/             (variaveis de ambiente)
      plugins/            (jwt, prisma, documentacao)
      modules/
        auth/ organizacao/ contrato/ lote/ equipamento/
        movimentacao/
          (cada modulo com controller, service, repository,
           rotas e schemas)
      shared/             (erros e utilitarios)
    prisma/
      schema.prisma
      seed.ts
  Papel de cada camada [PDF]:
   - Controller: recebe a requisicao HTTP, interpreta parametros
     e delega ao service.
   - Service: toda a logica de negocio (validacoes, transicao de
     status, calculos financeiros).
   - Repository: usa o Prisma Client; ponte entre dominio e
     tabelas.
  Por que [PDF]: a logica de negocio fica imune a mudancas na
  interface (HTTP, CLI ou mensageria no futuro).

PASSO 5 - Configurar variaveis de ambiente   [PDF: porta
          configuravel por variavel de ambiente]
  - Abra o .env (raiz da AV2) e deixe, no minimo:
      PORT=3333

      JWT_SECRET="uma-chave-longa-e-aleatoria"
      JWT_EXPIRES_IN="1h"
  - Troque SUA_SENHA pela senha do usuario postgres.
  - [PRATICA] Crie tambem um .env.example (sem segredos) e use

 FASE B - BANCO DE DADOS (PRISMA + POSTGRESQL)
==============================================================

PASSO 6 - Instalar e iniciar o Prisma   [PDF: Prisma ORM]
  npm i @prisma/client
  npm i -D prisma
  npx prisma init
  - Depois do init, abra o .env e confira se a DATABASE_URL e a

  - Se a sua versao do Prisma gerar prisma.config.ts ou pedir
    "driver adapter", siga a documentacao da versao instalada.

PASSO 7 - Escrever o schema.prisma   [PDF: replicar o modelo de
          dominio]
  Modelos: Organizacao, Contrato, Lote, Equipamento, Movimentacao
  (+ Usuario para o login).
  Relacionamentos [PDF]:
    - Organizacao tem 1 Contrato OPCIONAL e MUITOS Lotes.
    - Lote tem MUITOS Equipamentos.
    - Equipamento tem MUITAS Movimentacoes.
  Tambem [PDF]:
    - Campo "versao" em cada modelo (versionamento otimista).
    - Unique em CNPJ e em codigoBarrasInterno.
    - Tipos avancados do PostgreSQL: UUID para ids; JSON para
      dados semiestruturados, como as clausulas dos contratos.
  Exemplo de partida (ajuste aos campos da sua AV1):

    generator client { provider = "prisma-client-js" }
    datasource db { provider = "postgresql"  url = env("DATABASE_URL") }

    enum Papel { ADMIN OPERADOR }

    model Usuario {
      id        String @id @default(uuid())
      email     String @unique
      senhaHash String
      papel     Papel  @default(OPERADOR)
      versao    Int    @default(1)
    }
    model Organizacao {
      id       String    @id @default(uuid())
      nome     String
      cnpj     String    @unique
      contrato Contrato?
      lotes    Lote[]
      versao   Int       @default(1)
    }
    model Contrato {
      id            String      @id @default(uuid())
      organizacaoId String      @unique
      organizacao   Organizacao @relation(fields: [organizacaoId], references: [id])
      clausulas     Json?
      valor         Decimal     @db.Decimal(12, 2)
      inicio        DateTime
      fim           DateTime?
      versao        Int         @default(1)
    }
    model Lote {
      id            String        @id @default(uuid())
      organizacaoId String
      organizacao   Organizacao   @relation(fields: [organizacaoId], references: [id])
      equipamentos  Equipamento[]
      versao        Int           @default(1)
    }
    model Equipamento {
      id                  String         @id @default(uuid())
      codigoBarrasInterno String         @unique
      status              String
      loteId              String
      lote                Lote           @relation(fields: [loteId], references: [id])
      movimentacoes       Movimentacao[]
      versao              Int            @default(1)
    }
    model Movimentacao {
      id            String      @id @default(uuid())
      equipamentoId String
      equipamento   Equipamento @relation(fields: [equipamentoId], references: [id])
      statusAnterior String
      statusNovo     String
      criadoEm      DateTime    @default(now())
      versao        Int         @default(1)
    }

  (Os status podem virar enum conforme as regras da sua AV1.)

PASSO 8 - Criar a primeira migracao   [PDF: migracoes
          versionadas]
  npx prisma migrate dev --name init
  npx prisma generate
  - As migracoes geram arquivos SQL que descrevem as alteracoes
    e permitem evoluir o banco de forma controlada.
  - Se criar as tabelas sem erro, a conexao esta correta.
  - Para ver as tabelas: npx prisma studio  (ou pgAdmin).

 FASE C - SERVIDOR HTTP
==============================================================

PASSO 9 - Montar o servidor Fastify   [PDF: Fastify recomendado;
          Express aceito]
  npm i fastify
  - Criar app.ts que monta o Fastify com logging, registra
    plugins e rotas (arquitetura baseada em plugins).
  - Rotas declaradas de forma declarativa, com hooks para
    autenticacao e logging.
  - Criar um plugin que instancia UM PrismaClient e o disponibiliza
    para os repositories.
  - Rota de teste: GET /health -> { "status": "ok" }.
  - Se optar por Express, lembre de AVALIAR e JUSTIFICAR
    (escalabilidade e complexidade das validacoes).

PASSO 10 - Porta por variavel de ambiente e graceful shutdown
           [PDF]
  - server.ts le PORT do .env e inicia o servidor.
  - Graceful shutdown: ao receber SIGINT/SIGTERM, parar de aceitar
    novas conexoes, finalizar as ativas, fechar o Prisma e so
    entao encerrar o processo.
  - Teste: npm run dev, abrir /health, dar Ctrl+C e ver o log de
    encerramento.

PASSO 11 - Tratamento de erros padronizado   [PRATICA, apoia o
           PDF: "tratamento de erros mais estruturado"]
  - Erros de negocio (400/422), nao encontrado (404), conflito
    (409), nao autenticado (401), sem permissao (403).
  - Um error handler converte tudo em JSON padronizado.
  - Erros do Prisma: P2002 (unique violado) -> 409;
    P2025 (nao encontrado) -> 404.


==============================================================
 FASE D - REGRAS DE NEGOCIO (CAMADAS)
==============================================================

PASSO 12 - Repositories (Prisma Client)   [PDF]
  - Um repository por modulo: criar, buscar, listar, atualizar,
    remover.
  - So essa camada conhece o Prisma.
  - Usar eager loading (include) e selecao de campos (select)
    para otimizar as consultas.
  - Permitir receber o cliente de transacao (tx) como parametro.

PASSO 13 - Services (logica de negocio)   [PDF]
  Trazer da AV1 para os services:
   - validacoes;
   - regras de transicao de status dos equipamentos;
   - calculos financeiros.
  Services nao conhecem HTTP (nao usam request/reply).

PASSO 14 - Transacoes   [PDF: $transaction]
  Usar prisma.$transaction nas operacoes que precisam ser
  "tudo ou nada":
   - criar um lote com a adicao de varios equipamentos;
   - atualizar o status de um equipamento COM o registro da
     movimentacao.
  Objetivo [PDF]: manter a integridade referencial; alteracoes
  confirmadas juntas ou nenhuma persistida.

PASSO 15 - Versionamento otimista   [PDF]
  - Em todo update, filtrar pelo id E pela versao lida, e
    incrementar a versao.
  - Se nenhuma linha for atualizada, devolver conflito (409):
    alguem alterou o registro antes.
  - Objetivo [PDF]: evitar atualizacoes perdidas.

PASSO 16 - Controllers e rotas REST   [PDF]
  - Controllers finos: recebem a requisicao, interpretam
    parametros, delegam ao service, devolvem a resposta.
  - Validar entrada com JSON Schema do Fastify (body, params,
    querystring, response).
  - Rotas por recurso (organizacoes, contrato, lotes,
    equipamentos, movimentacoes) com codigos HTTP corretos
    (200, 201, 204, 400, 401, 403, 404, 409).

 FASE E - SEGURANCA
==============================================================

PASSO 17 - Autenticacao com JWT   [PDF]
  npm i @fastify/jwt
  npm i bcrypt   (use a MESMA biblioteca de hash que usou na AV1;
                  se bcrypt nativo falhar no Windows, bcryptjs tem
                  a mesma API)
  - A API e stateless: as sessoes do CLI sao substituidas por
    JWT.
  - Fluxo de login [PDF]:
      1. Receber as credenciais.
      2. Verificar o hash da senha armazenado no banco.
      3. Em caso de sucesso, gerar token JWT com o identificador
         do usuario e o papel.
      4. Enviar o token ao cliente.
      5. O cliente inclui o token no cabecalho Authorization em
         todas as requisicoes seguintes.
  - Hook/middleware global do Fastify valida o token em cada
    requisicao e injeta os dados do usuario no objeto de
    requisicao (login e /health ficam publicos).

PASSO 18 - Autorizacao por papel   [PDF]
  - Os services consultam o papel do usuario para aplicar as
    regras de autorizacao (ex.: ADMIN x OPERADOR).
  - Papel insuficiente -> 403.
